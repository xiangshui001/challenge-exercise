# 13｜GitHub 与服务器项目同步约定

用户要求每完成一段工作就更新 GitHub，尽量保持服务器与仓库结构一致。此约定按阶段执行，不创建定时任务，不自动访问服务器。

## 一份代码树

服务器项目目录应是这个仓库的 Git checkout。外层目录名允许不同，但 data/models/train/evaluation/configs/checkpoints 等相对路径按 [12](12_TRAINING_ROADMAP.md) 保持一致。数据/权重/特征/原始运行日志存在服务器本地并被忽略；同结构不等于公开相同大文件。

当前服务器仅确认曾计划创建 `~/siglip-retrieval`，其实际文件列表尚未提供，所以**尚未验证两端一致**。有现成代码/数据时先保留，检查 `git status` 和目录，不直接 clone 到非空目录、不覆盖未提交文件。

## 每个阶段的交接

1. 开工时记录分支和 commit；工作区干净才 `git pull --ff-only`。PR 未合并时使用对应 PR 分支，不把“PR 已上传”说成 main 已更新。
2. 阶段完成后检查改动，提交代码、配置与文档；运行记录包含实际命令、模型/数据版本、依赖、真实结果、失败或未运行部分。
3. 更新 `docs/14_PROGRESS_LOG.md`。如运行过模型，把模型加载/训练/评测各阶段成本和输出路径写清，不把示例数值当结果。
4. 公开提交前检查文件清单，排除图片/权重/密钥/原始未审查日志。提交为一个清楚的阶段 commit，推送工作分支并建立/更新 PR。
5. 用户审阅合并后，另一端在干净工作区拉取，并记录相同 commit。服务器侧修改先提交/推送，云端侧基于该 commit 继续；有冲突时先检查双方差异，不使用强制覆盖。

默认同步节点：环境确认、推理小试、基线、训练小试、完整微调、验证优化、最终报告。一个阶段很长时，完成一个可复现的小步骤也可提交，不等到全部结束。

## 查看实际结构和版本

在服务器项目根目录执行：

```bash
git status --short
git branch --show-current
git rev-parse HEAD
python scripts/project_state.py --out runs/sync/current.json
```

最后一条只读取 Git 跟踪文件的路径/哈希和必要目录状态，写到被忽略的本地 runs 目录；不读密钥/原始图像/权重，不联网、不加载模型。把报告内容或相关摘要发回云端即可比对；文件的系统绝对路径和账号无需提供。

暂时没 Git 时先只查看已有文件。首次 clone 要选择空的新目录，确认后再迁移自己的脚本和数据；具体迁移以服务器实际结构为准，不执行破坏性搬移。
