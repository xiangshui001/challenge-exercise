# 05｜执行规划、预算与里程碑

以下是熟悉 Python、能够取得数据和权重时的**人力规划估计**，不是 A100 跑分或供应商报价。单张 A100 的显存、共享情况和可用时段需要开工时登记。不给尚未测量的推理速度或 API 费用填确定数。

## 1. 基础版：约 3 个工作日

| 阶段 | 人工投入估计 | 工作与产物 |
|---|---:|---|
| D1 | 4–6 小时 | 环境小试、固定数据清单、指标单元测试、数据审计 |
| D2 | 4–6 小时 | B0/B1 验证集编码与比较；F1 廉价试验；错误样本抽取 |
| D3 | 4–6 小时 | 配置冻结、正式测试、置信区间、结果表和基础报告 |

基础版预计人工投入 12–18 小时，下载等待和 GPU 占用另记。达到这一档后已经具备实验五的评估、优化与复测链条，不以研究扩展为前置。

## 2. 研究版：总计约 5–7 个工作日

| 日程 | 重点 | 当天验收物 |
|---|---|---|
| D1 | 环境、数据与指标正确性 | data_audit、指标测试、环境记录 |
| D2 | B0/B1/F1，确定强基线 | 验证指标、逐查询记录、初步错误类型 |
| D3 | Qwen 适配与 100 查询小试 | 候选覆盖率、重排收益、速度和显存记录 |
| D4 | R1、G25/G50 与随机对照 | 验证质量—候选对数表、冻结参数草案 |
| D5 | val_confirm，一次确认后冻结；正式测试 | 冻结配置、测试结果与 bootstrap |
| D6 | 错误复核；有余力做 200 查询改写诊断 | 修复/退化案例、诊断表 |
| D7 | 结果核对、报告、答辩材料和缓冲 | 可复算证据包、最终报告 |

研究版预计人工总投入约 28–42 小时。若 D3 显示重排无收益或预计耗时超出可用机时，不延长为训练项目：保留失败实验并收尾基础版。200 查询改写属于可选项，可在时间不足时减为预先定义的较小规模并明确记录，不按结果筛选。

## 3. 重排工作量怎么估计

这里的“全量重排”仅指所有查询的 Top-M 候选。设查询数 Q、候选数 M、启用比例 p：

$$Pairs=Q\times M\times p.$$

| 场景 | 计划查询 | M | 理论图文对数 |
|---|---:|---:|---:|
| 小试 | 100 | 50 | 5000 |
| 单个完整划分、全部查询 | 5000 | 50 | 250000 |
| 单个完整划分、约 25% 查询 | 5000 | 50 | 约 62500 |
| 单个完整划分、约 50% 查询 | 5000 | 50 | 约 125000 |
| 验证与测试都全查询重排 | 10000 | 50 | 500000 |

门控分位数来自验证集，测试实际比例可能不同；以实际触发数核算。批处理可减少 Python 或网络调用次数，但不会消除模型处理的图文对数量。

小试得到吞吐 v 对/秒后估算 T≈Pairs/v，再乘以执行者选定的安全余量，并加上模型加载、图片读取和失败重试成本。**先填实测速率，再决定是否执行 50 万对**。本方案不预先批准或启动该规模任务。

## 4. API 预算

基础版不依赖 API。错误分析可先处理 50 组案例；改写诊断最多 200 条原句、每条两条改写。不要把“API 可接入”理解成无限调用预算。

调用前填写供应商、模型快照、输入/输出计费方式、单图像计费规则、请求配额、允许金额上限和失败重试上限。对 10 个典型请求做小试，根据真实 usage 估算总额；上限未设定时不启动批量 API 任务。不要在仓库写实际密钥。

调用日志记录 attempted/succeeded/failed、token、图像计费单位、缓存命中和金额。只有供应商价格与 usage 都明确时才换算费用，未知值保持 null，不猜测“只需几元”。

## 5. 五个阶段门

| 阶段门 | 放行条件 | 不满足时 |
|---|---|---|
| G0 数据 | 数量、ID、正例、文件全部通过检查 | 停止正式评测并修数据 |
| G1 基线 | 指标测试通过；B0/B1 结果可由预测重算 | 修实现，不立刻换更大模型 |
| G2 重排小试 | 配对输入正确、预算可接受、有分析价值 | 退回基础版或保留负结果 |
| G3 参数冻结 | val_confirm 完成、无测试集反馈调参 | 不运行最终 test 或标明探索性质 |
| G4 交付 | 结果、配置、预测、案例和引用一致 | 补证据，不填猜测成绩 |

## 6. 停止规则

依赖问题超过约 2 小时先缩小技术栈；处理器和数据错误优先于改模型；最多先试 5 个 F1 权重、3 个重排融合权重及 2 个门控预算；不在第一轮增加多个骨干、LoRA 或多轮生成。预算或耗时触顶时保留已有结果及失败日志，不自动追加 API 支出。

## 7. 人工与模型助手分工

交互式编码助手负责模块实现、数据审计、指标测试和模板填充；执行者负责服务器访问、数据使用条件、预算设置、启动机时、人工复核和结果签字。模型助手可以生成解释草稿，但不能决定把何种失败样本排除，也不能把参考文献中的成绩当作本地结果。
